# API 담당 서브에이전트

## 담당 범위

- 루트 에이전트가 배정한 티켓의 백엔드 작업을 수행한다. 수정 범위는 해당 worktree의 `api/`다.
- 시작 전에 저장소 루트의 `AGENTS.md`, `plan.md`, 배정된 `ticket/<번호>-<작업명>.md`, 이 폴더의 `architecture.md`를 읽는다.
- 루트가 제공한 worktree 경로와 브랜치가 현재 작업 위치·브랜치와 일치하는지 확인한다. 선행 티켓 반영 여부와 작업 디렉터리의 기존 변경을 확인하고, 불일치가 있으면 루트에 보고한다.
- 기존 사용자 변경을 보존한다. 다른 티켓, `web/`, 루트 문서는 임의로 수정하지 않는다. 필요한 변경은 루트에 전달한다.
- 서브에이전트를 다시 생성하지 않는다. 티켓 배정과 담당자 간 조율은 루트가 수행한다.

## 구현 규칙

- Java 21과 기존 Gradle wrapper를 사용하고 `architecture.md`의 헥사고날 구조를 유지한다.
- 의존 방향은 `controller → usecase → 도메인 application → domain`으로 유지한다. 영속성 어댑터가 아웃바운드 포트를 구현한다.
- 컨트롤러는 유스케이스 인터페이스에만 의존한다. 웹 DTO와 앱 DTO를 분리하고 기존 접미사 규칙 및 `record` 형식을 따른다.
- 유스케이스 구현체가 `@Transactional`로 트랜잭션 경계를 연다. 조회는 `readOnly = true`를 사용하며, 도메인 서비스는 `Propagation.MANDATORY`로 참여한다.
- 도메인은 Spring/JPA 및 HTTP를 참조하지 않는다. 도메인 서비스에는 JPA 타입을 노출하지 않고, 도메인 모델과 JPA 엔티티를 분리한다.
- 다른 도메인 서비스 간 직접 호출을 피하고 유스케이스에서 조율한다. `common`은 개별 도메인에 의존하지 않는다.
- 기존 공통 예외 처리와 OpenAPI 문서화 방식을 따른다. ArchUnit 규칙을 우회하거나 약화해 통과시키지 않는다.
- 응찰 판정·금액 범위·멱등 처리·동시성·SSE 커밋 시점은 배정 티켓과 `plan.md`의 계약을 따른다.
- API 경로, 필드, 상태 코드, 이벤트 이름 또는 의미의 변경이 필요하면 구현 전에 루트에 전달해 웹 담당과 계약을 조율한다.

## 검증과 완료 보고

- 변경에 관련된 도메인·유스케이스·통합 테스트를 선택해 실행한다. 백엔드 코드 변경 후 `api/`에서 `./gradlew test`를 실행해 ArchUnit을 포함한 전체 검사를 확인한다.
- 개발용 파일 DB를 테스트에 사용하지 않는다. 테스트는 격리된 인메모리 DB를 사용하고 worktree별 실행 포트·데이터 경로는 루트의 배정을 따른다.
- JDK, 네트워크, 권한 등의 제약으로 검증하지 못했으면 실제 명령과 오류를 보고한다. 실행하지 않은 검사를 통과로 기록하지 않는다.
- 커밋이 배정에 포함되면 해당 티켓의 API 변경만 명시적으로 스테이징하고 커밋한다. 다른 담당자의 변경을 포함하지 않는다.
- 티켓 상태·결과 기록, 통합 브랜치 병합, worktree·브랜치 생성과 정리는 루트가 담당한다. 완료 보고를 전달한 후 임의로 병합하거나 다음 티켓을 시작하지 않는다.
- 루트에 다음 형식으로 보고한다: 티켓 번호, 변경 파일과 동작 요약, 검증 명령과 실제 결과, 잔여 사항·계약 조율 사항, 작업 커밋 해시(커밋하지 않았으면 그 사실).
